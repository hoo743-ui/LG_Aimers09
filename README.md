# LG Aimers 9기 Phase 2 — 투구 제구 성공 확률 예측

투구 직전까지 확인 가능한 정보만으로 각 투구의 **제구 성공 확률**을 예측한다.
평가지표는 **Brier Skill Score** — 확률의 순위가 아니라 확률값 자체의 정확도를 잰다.

```
Score = max(0, 100000 × (1 − Brier / r(1−r)))      r = 해당 평가셋의 실제 성공률
```

즉 **Score ≈ BSS × 100,000**. Brier 를 기준선 대비 1% 줄이면 1000점이다.

### 로컬 ↔ LB 환산 — 🚫 직선은 폐기했다. 델타 x 0.5 만 쓴다

**9회차가 직선을 깼다.** 5점 직선(`LB ≈ 1.146 × 로컬 + 73.2`)으로 로컬 748.77 은
**931.0** 이 나와야 했지만 실제는 **864.92** — 오차 **−66.0** 이다. 6점으로 다시
적합해도 잔차가 −44 ~ +25 로 벌어져 관계 자체가 직선이 아니다.

```
5점 직선   LB = 1.146 x 로컬 + 73.2    잔차 +0.4 / +10.1 / +0.1 / +1.8 / -12.4
6점 재적합  LB = 1.042 x 로컬 + 128.6   잔차 -12.1 / +25.0 / +16.8 / +13.1 / +1.2 / -44.1
```

**대신 델타 환산비는 세 번 연속 맞았다.** 이제 이것만 쓴다.

| 회차 | 고친 것 | 로컬 델타 | LB 델타 | 비율 |
|---|---|---|---|---|
| 4 | 해상도 | +16.97 | +9.40 | 0.554 |
| 7 | 해상도 | +21.94 | +10.98 | 0.500 |
| 9 | 해상도 | +81.29 | +39.44 | **0.485** |
| **10** | **어긋남(보정)** | **+13.97** | **+47.49** | **3.40** |

**환산비는 하나가 아니다.** 해상도(신호)를 올리는 개선은 세 번 연속 0.485~0.554
였다 — 로컬 +81 이라는 큰 폭에서도 유지됐으니 작은 개선 전용 근사가 아니다.
그런데 10회차는 **3.40** 이었다. 이유는 4-24 에 있다: 로컬 2024 의 어긋남은 43.9
인데 평가 시즌의 어긋남은 훨씬 크고(위반 국면보정이 LB +57.65 를 벌었던 것이 그
크기다), 로컬로는 2024 의 어긋남만큼만 보이기 때문이다.

> **계획에 쓰는 방식이 둘로 갈린다.**
> - **해상도 축** — 로컬 델타 × 0.5. LB +10 을 원하면 로컬 +20 이 필요하다
> - **보정 축** — 로컬에서 작아 보여도 평가 시즌에서 배가 된다. **로컬 크기로
>   기각하지 말 것.** 규칙 ⑥의 10점 문턱을 이 축에 적용하면 alpha 를 버렸을 것이다
>
> 1등(1000+)까지 약 88점 남았다. 보정 축에 40~50 이 더 있을 수 있다 (역산 최적
> alpha 1.30 에서 예상 956).

### 2-2. 환경 구성

**제출 환경과 패키지 버전이 정확히 일치해야 한다.** 모델 pkl 은 학습한 sklearn
버전으로 직렬화되므로, 다른 버전으로 만들면 평가 서버에서 로드가 깨질 수 있다.

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -U pip -r requirements.txt
.\.venv\Scripts\python.exe -c "import sklearn,joblib,pandas,numpy; print(sklearn.__version__, joblib.__version__, pandas.__version__, numpy.__version__)"
# 기대 출력: 1.7.2 1.5.3 2.3.3 2.2.6
```

**확인 명령에 numpy 를 반드시 포함할 것.** 예전 확인 명령은 sklearn·joblib·pandas
셋만 찍었고, 그래서 numpy 가 2.5.1 로 밀려 있는 걸 오래 못 봤다 (아래 🚨).

> **핀은 1.7.2 다.** 중요한 건 절대 버전이 아니라 **pkl 을 만든 sklearn 버전과
> `requirements.txt` 핀이 같은 것**이다. 1.7.2 는 Python 3.10~3.13 을 지원해
> 평가 서버의 파이썬이 무엇이든 설치가 되지만, 1.8.0 은 3.11 이상을 요구해
> 서버가 3.10 이면 **설치 단계에서 실패한다.** 그래서 낮은 쪽으로 맞춘다.

> 🚨 **학습 환경이 핀과 어긋나 있었다 (2026-08-06 발견).** `.venv` 는 실제로
> sklearn **1.8.0** / numpy **2.5.1** 이었는데 `requirements.txt` 는 1.7.2 /
> 2.2.6 을 시킨다. 그 상태로 만든 pkl 은 **1.8.0 이 절인 것을 서버가 1.7.2 로
> 푸는** 형국이라 6-4 와 같은 종류의 로드 실패를 부른다.
>
> 제출물 학습은 **핀과 정확히 일치하는 `venv_submit`** 에서 한다.
>
> ```powershell
> python -m venv venv_submit

> # 기대 출력: 1.7.2 1.5.3 2.3.3 2.2.6

>
> `.venv` 는 실험 전용으로 둔다 — 상대 비교만 하므로 버전이 달라도 무방하다.

### 2-3. 실험 루프 복구 (2026-08-10 이후)

**실험 캐시는 저장소에 없다** (`exp/cache` 572MB, `exp/preds` 84MB — 둘 다

뒤의 둘은 **이미 기각된 피처**라 새 실험에 꼭 필요하지는 않다. 다만
`plans/exp004`, `exp012` 를 재현하려면 있어야 한다. 순서는 지켜야 한다 —
`prep.py` 가 만든 캐시에 나머지가 컬럼을 덧붙이는 구조다.

`exp/preds/*.npz`(검증 예측)는 재생성에 학습이 필요하다. 없으면 `runner.py` 가
그냥 다시 학습하므로 **정확성 문제는 없고 시간만 든다.** 전체 재현은 약 5시간
(297 fits) 이고, 결론은 전부 `experiment_log.csv` 와 4-10~4-12 에 있으므로
보통은 다시 돌릴 필요가 없다.

**실험 한 판 돌리는 법:**

```powershell
# plans/*.json 을 하나 만들고 (기존 것 복사가 빠르다)
$env:OMP_NUM_THREADS=11
.\.venv\Scripts\python.exe exp\runner.py --plan plans\exp016.json --shard 0 --nshard 2
.\.venv\Scripts\python.exe exp\analyze.py --exp exp016 --ref cat_tuned
```

> 🚨 **CatBoost 실험은 `hparams.threads` 를 반드시 넣을 것.** 스레드 수가
> 결과를 바꾼다 (fold2024 seed42 에서 6스레드 717.97 vs 11스레드 712.29).
> 지금까지의 CatBoost 기록은 전부 `threads: 11` 로 잰 것이라, 다른 값으로
> 재면 기존 기록과 비교할 수 없다. **새 PC 의 코어 수와 무관하게 11 로 둘 것.**
>
> 샤드 실행 시 `OMP_NUM_THREADS` 도 같이 맞춰야 실제로 11 스레드가 쓰인다.

> **로그 동시 기록 주의.** 샤드 여러 개가 `experiment_log.jsonl` 에 동시에
> append 하면 줄이 섞일 수 있다. 진실은 `exp/preds/*.npz` 에 있으므로,
> 샤드가 끝난 뒤 `runner.py --plan <같은 plan>` 을 **단일 프로세스로 한 번 더**
> 돌리면 캐시에서 로그가 깨끗하게 복구된다. 읽는 쪽은 깨진 줄을 건너뛴다.

## 4. 알아낸 것

### 4-1. 이 문제는 "표현력"이 아니라 "과신하지 않기" 싸움이다

| 모델 | 2024 검증 |
|---|---|
| RandomForest `max_depth=10` (베이스라인) | 415.57 |
| HGB 조기종료 (`validation_fraction=0.1`) | **379.01** |
| HGB 256회 (곡선에서 최적점 선택) | 627.05 |
| HGB L10 `min_leaf=1000` 1000회 | **640.01** |

sklearn 의 조기종료는 **학습 데이터 안에서 무작위로** 10% 를 떼기 때문에 같은
시즌끼리 비교하게 되고, 시즌이 바뀔 때의 일반화 실패를 감지하지 못한다. 그래서
수백 회를 더 돌아 과신 상태로 갔다(예측 범위가 0.28~0.72 까지 벌어짐).

**반드시 시즌 단위 홀드아웃으로 반복수를 정할 것.** `staged_predict_proba` 를 쓰면
학습 한 번으로 전체 곡선이 나온다 (`diag_curve.py`).

잎 개수 봉우리는 L10 근처다. 잎이 적을수록 반복수는 늘어난다.

```
L4 587.99   L7 608.12   L10 640.01 ★   L15 632.38   L31 627.74   L63 602.29
```

### 4-2. 타깃 비율이 해마다 떨어진다 — 가장 중요한 구조적 사실

| 시즌 | 실제 성공률 | 누적 `asof_pitcher_success_rate` | `asof_..._prev1_game` |
|---|---|---|---|
| 2019 | 0.5647 | 0.5598 | 0.5613 |
| 2020 | 0.5327 | 0.5472 | 0.5340 |
| 2021 | 0.5328 | 0.5355 | 0.5291 |
| 2022 | 0.5289 | 0.5354 | 0.5268 |
| 2023 | 0.5000 | 0.5237 (**−0.024**) | 0.5044 (−0.004) |
| 2024 | 0.4861 | 0.5114 (**−0.025**) | 0.4884 (−0.002) |

**누적형 `asof` 는 경력 전체 평균이라 하락을 뒤늦게 따라간다.** 최근 2년은 0.025 나
뒤처진다. 반면 `prev1_game` 계열은 현재 국면을 거의 정확히 반영한다.

중심이 `d` 만큼 어긋나면 `d²/r(1−r)×100000` 점을 잃는다. 2024 폴드의 편차 0.0119 는
57점이다. 연도별 난이도가 극단적으로 갈리는 이유다.

```
2021 → 1192.84     2022 → 2249.51     2023 → 0.00     2024 → 639.04
```

> **2023 형 붕괴는 중심 보정으로 못 막는다.** 정답 성공률로 중심을 완벽히 맞춰도
> 2023 은 여전히 0.00 이다. 중심을 제거하고 남는 실력이 상수 예측보다 못하다는
> 뜻이다(BSS 음수 → `max(0,...)`). 국면이 바뀌면 중심만 어긋나는 게 아니라 피처와
> 타깃의 관계 자체가 끊어질 수 있고, 그때는 어떤 사후 보정도 소용없다.

### 4-3. 국면 보정 🚫 규칙 위반 — 쓰지 말 것

평가셋 전체의 `prev1` 평균으로 예측 중심을 옮기는 방법이다. 2024 폴드에서 +54,
리더보드에서 549.64 → 862.75 를 만든 핵심이었다. **그리고 규칙 위반이다.**

```
data_description.md 5) 금지 예시
  - test.csv 내부 빈도값 또는 분포 통계
  - 평가 데이터 전체를 보고 만든 사후 보정값     ← 이것
```

판단이 어긋난 지점 — "평가셋의 **정답**을 안 보니 괜찮다"고 생각했다. 규칙이 금지하는
건 정답 참조가 아니라 **다른 행 참조**다. 3·4회차 제출(862.75, 872.15)이 이 상태이고,
보정을 뺀 실력은 로컬 645.54 / LB 약 817 이다.

`script.py` 에서 제거했다. 같은 이유로 `detrend`(평가셋 리그 평균 차감)도 제거했다.

**추정기 자체는 유효한 관측이다.** 다른 용도로 쓸 수 있으니 남긴다 — `prev1` 의
단면 평균은 그 시즌 성공률을 **평균 오차 +0.0002, 표준편차 0.0031** 로 맞힌다.
누적형이 최근 두 해에 0.024 씩 밀리는 것과 대조적이다.

**합법 대체 수단은 찾지 못했다.** 시도와 결과는 4-5 에 있고, 2026-08-06 에
워크포워드로 다시 확인했다 (`center_test.py`).

합법의 경계부터 분명히 해두면 이렇다.

```
❌ 평가셋 prev1 평균으로 중심 이동           4-3, 위반
❌ 우리 예측값을 평가셋에서 평균내어 이동     구조적으로 같은 위반
✅ 학습 데이터만으로 정한 상수를 더하기       행 독립, 평가셋 미참조
```

세 번째만 남으므로 `p' = p + Δ` 이고 Δ 는 pkl 에 박히는 수다. 그 Δ 를 이전
폴드들에서만 추정해(워크포워드) 평가했다.

| fold | 실제 | 예측평균 | 편향 |
|---|---|---|---|
| 2021 | 0.5328 | 0.5232 | **−0.0096** |
| 2022 | 0.5289 | 0.5300 | +0.0011 |
| 2023 | 0.5000 | 0.5216 | +0.0217 |
| 2024 | 0.4861 | 0.4981 | +0.0120 |

평균 +0.0063, 표준편차 0.0135, **부호가 뒤집힌다.**

```
wf_bias   (이전 폴드 평균 편향만큼 이동)   평균  -3.55   1승 2패
wf_trend  (시즌 성공률 선형 외삽)          평균 -25.83   1승 2패
```

2024 에서는 둘 다 도움이 됐지만(+34.30 / +44.25) 2022 에서 크게 잃는다(−44.94 /
−121.73). **기대값이 음수라 채택할 수 없다.**

> **왜 위반판은 그렇게 잘 됐나 — 그리고 왜 합법으로는 못 따라가나.** 평가셋
> 전체를 평균내면 24.5만 행이 잡음을 지워 그 시즌 성공률을 표준편차 0.0031 로
> 맞힌다. 행 독립을 지키면 각 행은 자기 `prev1` 하나뿐이고 그건 한 경기치라
> 잡음이 크다. 모델은 이미 `prev1` 을 피처로 갖고 있고 그 잡음-신호 저울질을
> **스스로 최적화**하고 있다. 즉 **평균 내기를 금지당한 이상, 중심을 정밀하게
> 맞추는 것은 구조적으로 불가능하다.** 이건 아이디어가 부족해서가 아니다.

### 4-4. Trackman 연결 — 성공했지만 점수는 안 올랐다

기존 결론("ID 체계가 달라 조인 불가")은 **틀렸다.** ID 직접 비교만 확인하고 접었던
것이 오판이다. 경기를 맞추면 대응표를 역산할 수 있다.

`trackman_link.py` 의 부트스트랩 3단계:

1. `(시즌, 월, 요일, 투구수)` 가 양쪽에서 유일한 경기부터 맞춘다 (42.3%)
2. 그 매칭에서 **팀 코드 ↔ 팀 id 를 다수결로 역산** — 알고리즘은 팀 이름을 모른다
3. 팀 대응표로 나머지를 확정 (64.9%), 경기 안에서 투수를 등판 순서·투구 수로 짝짓는다

```
팀 13개 — KBO 10구단 + KBO_POL, KBO_ARM, MIN_HAW  (train 의 팀 id 개수와 일치)
투수 592명 / 792명, 신뢰도 90% 이상 전원, 중앙값 100%, 중복 배정 0
→ pitcher_id_map.csv
```

팀 이름을 모르는 상태에서 KBO 10구단이 정확히 복원된 것이 매칭이 옳다는 증거다.
요일 규약(월=0)은 경기 수 대조로 확정했다.

**그런데 물리 프로필 피처는 실패했다** (3폴드, base 대비): 전체 26개 **−17.17**,
릴리스 반복성 4개만 **−5.95**. 커버리지는 충분했다(학습 97.6% / 검증 79.0% —
검증 상한은 매칭이 아니라 선수 유입률이 정한다. 2024 는 투구의 19.9% 가 신인).

**왜 실패했나.** `pitcher_id` 가 이미 투수를 식별한다. 프로필은 투수당 값 하나인
**정적 상수**라, 트리 입장에서 이미 아는 대상을 다른 좌표계로 다시 말하는 것에
가깝다. ID 복원이 +8.5 였던 것의 뒷면이다. 게다가 2025 예측에 쓸 수 있는 trackman 은
2024 가 최신이라 "지금의 반복성"을 말할 수 없다.

> **대응표는 그대로 쓸 수 있다.** 정적 프로필이 아닌 활용법 — `pitcher_id` 를 빼고
> 프로필로 대체(미지 투수까지 커버), 시즌별 프로필의 **변화량** — 은 미검증이었다.
> 앞의 것은 아래에서 기각됐고, 뒤의 것은 4-7 에 있다.

#### `pitcher_id` 대체안 기각 — 미지 투수는 trackman 에도 없다

"프로필로 `pitcher_id` 를 대체하면 미지 투수에게도 물리 정보가 붙는다"는 제안은
**전제가 틀렸다.** 모델을 돌리기 전에 커버리지만 세어 확인할 수 있었다
(`dyn_probe.py`). 미지 = 그 폴드의 학습 시즌에 없던 `pitcher_id` 다.

| fold | 미지 투수 투구 비율 | 미지 투수 수 | 프로필 보유 | **미지 투구 중 프로필** |
|---|---|---|---|---|
| 2021 | 20.6% | 95 | 12 | **6.0%** |
| 2022 | 15.7% | 88 | 4 | **1.4%** |
| 2024 | 19.9% | 81 | 2 | **3.1%** |

당연한 결과다 — train 과 trackman 은 **같은 리그의 같은 기간**을 담는다. train 에
처음 나타난 투수는 trackman 에도 처음이라 과거 프로필이 있을 수 없다. 신인에게
물리 정보를 붙이려면 데뷔 전 데이터가 필요한데 그런 건 제공되지 않는다.

따라서 이 안은 ID 복원의 **+8.5 를 내주고 미지 투구의 3% 를 덮는** 교환이다.
값싼 검산 하나가 학습 여러 번을 아꼈다 — **가설의 전제가 데이터로 셀 수 있는
것이면 모델을 돌리기 전에 세어볼 것.**

|---|---|---|
| 최근 시즌 가중 ×1.5/×2/×3 | −34 ~ −57 | 중심 편차는 거의 안 줄고 데이터 유효량만 깎인다 |

| 누적형 상대화 (`detrend`) | −11.0 | 절대 수준 자체가 정보다. 중심은 이미 따로 잡고 있었다 |
| 차분 피처 (누적형 − 최근형 9개) | −3.75 | 둘 다 주면 트리가 필요한 만큼 조합한다. 상관 높은 컬럼만 늘었다 |

| 경기 내 시간 구조 (`fatigue`) | −3.94 | 신호는 실재하나(투구수 구간별 0.4803→0.4969) **인과가 반대**다. 오래 던지는 건 잘 던지고 있다는 뜻이고 그건 `asof_*`·`inning` 이 이미 말한다 |

**채택된 것은 둘뿐이다** — 국면 보정(4-3, 규칙 위반으로 철회)과 `pitcher_id` 복원.

`pitcher_id`/`batter_id` 복원은 **+8.5**(24회 요인 실험 평균 +5.95, 잎 10 에서 +8.5).
과거에 "제거해도 차이 없음(±2)"으로 기록했던 것은 **보정 없이 잰 값**이었다. 폴드가
최근일수록 이득이 커진다(2021 −9.6 → 2022 +13.5 → 2024 +21.6) — 학습 시즌이 쌓일수록
ID별 표본이 늘어 과적합 재료가 아니라 진짜 개인차가 되기 때문이다. **팀 ID 는 항상
남길 것** (같이 빼면 −20.45).

> **이 데이터셋의 피처는 이미 잘 설계돼 있다.** `asof_*` 가 투수·타자 이력을 여러
> 시간 창으로 요약해 두었고, 위 기각 목록의 절반은 그 요약을 다른 형태로 다시
> 표현한 것이었다. 남은 개선은 피처가 아니라 **구조**에 있다.

### 4-6. 측정 방법 — 이걸 몰라서 잘못된 결론을 낼 뻔했다

**단일 폴드·단일 시드 측정은 믿을 수 없다.**

```
시드 노이즈    ±15  (같은 설정, fold 2024 에서 702.28 vs 687.68)
폴드 간 차이   ±45  (잎 효과가 2021 −44.5 / 2022 +31.5 / 2024 +18.4)
3폴드 평균     ±4   (시드 노이즈가 √n 으로 줄어든다)
```

fold 2024 에서 "잎 10→20 이 +23.3" 을 얻고 확정 직전까지 갔다. 24회 요인 실험
(잎 × ID × 3폴드 × 2시드)을 돌리니 실제 효과는 −0.72 였다. **그대로 제출했으면
제출 기회 하나를 −0.72 짜리 도박에 썼을 것이다.**

- 효과를 재려면 **최소 3폴드 × 2시드**. 폴드 안에서 비교하고(점수 스케일이 다르다)
  폴드별 부호가 갈리는지 반드시 확인할 것
- 2023 폴드는 어떤 구성으로도 0점이라 비교에 정보가 없다. 제외한다
- 곡선 최적점(`staged_predict_proba`)으로 재면 검증셋에 맞춘 낙관 편향이 있다.
  변형 간 비교에는 공정하지만 절대값은 부풀려져 있다
- **폴드별로 부호나 크기가 흔들리는 개선은 그 변동폭만큼 할인할 것.** 4회차에서
  로컬 +17 을 얻고 LB 는 +9.4 였다

### 4-7. Trackman 변화량 — 기각. 이로써 Trackman 은 고갈됐다

4-4 의 실패 진단은 "프로필이 투수당 상수라 `pitcher_id` 와 중복"이었다. 그렇다면
**변화량**은 그 비판을 피한다 — 작년 대비 구속 저하는 정체성이 아니라 상태이고,
같은 투수도 해마다 값이 다르다. `trackman_dyn.py` 로 쟀다.

시점 규칙은 그 투수가 **마지막으로 던진 두 시즌**(둘 다 행의 시즌 미만)의 차이다.
연속일 필요는 없고 공백은 `dtm_gap` 으로 따로 준다. 평가(2025)는 2024−2023 을
쓰고 학습 행도 같은 규칙이라 의미가 일치한다. 피처 5개 — 구속 평균, 릴리스 산포
3종(`rel_height`/`rel_side`/`extension`), 공백.

```
fold2024 seed42   base 640.01   delta 607.76   -32.25
fold2024 seed43   base 646.62   delta 620.80   -25.82
                                       평균    -29.04  (표준편차 3.22)
```

시드 노이즈 ±15 를 훨씬 넘고 부호도 일치한다. **명확한 손해다.**

**전제 검사는 통과했는데 결과는 실패했다.** 사전에 잰 산포는 이랬다.

| 양 | 투수간 표준편차 | 연도간 변화 표준편차 | 비 |
|---|---|---|---|
| `rel_speed` | 4.208 | 2.067 | 0.49 |
| `rel_height_std` | 0.016 | 0.018 | 1.11 |
| `rel_side_std` | 0.031 | 0.043 | 1.38 |
| `extension_std` | 0.013 | 0.014 | 1.05 |

비가 1 을 넘는 걸 "정체성이 아니라 진짜로 움직이는 값"이라고 읽었다. **그 해석이
틀렸다.** 한 시즌 300구로 추정한 산포의 표준오차가 그 안에 섞여 있다. 즉 비가 큰
것은 신호가 크다는 뜻이 아니라 **추정 오차가 크다**는 뜻이기도 했고, 모델 결과를
보면 후자가 지배적이었다. 최적 반복수가 1012 → 617 로 주저앉은 것이 방증이다 —
새 피처가 일반화가 아니라 **더 빠른 과적합**에 쓰였다.

커버리지 불균형도 겹쳤다. 변화량은 두 이전 시즌이 필요해 2019·2020 행에는 값이
없다. fold 2024 기준 **학습 30.9% / 검증 57.8%** 로, 모델이 이 피처를 거의 못 본
채로 검증에서는 절반 넘게 마주친다.

> **폴드 제약.** fold 2021 은 학습(2019~2020)에 변화량이 0% 라 구조적으로 쓸 수
> 없고, 2022 도 2021 한 해뿐이라 약하다. 4-6 의 '최소 3폴드'를 못 채운다. 다만
> 효과가 −29 로 크고 두 시드의 부호가 같아 결론은 뒤집히기 어렵다.

**정리 — Trackman 은 세 갈래 모두 닫혔다.** 정적 프로필(4-4) −5.95, `pitcher_id`
대체(4-4 하위절) 전제 오류, 변화량(여기) −29.04. 대응표를 만든 것 자체는 옳았고
그 과정은 재사용 가치가 있지만, **이 데이터에서 Trackman 으로 점수를 올리는 길은
없다고 본다.** 다음 작업은 7장의 2·3번으로 간다.

### 4-8. 상황별 분할 모델(MoE) — 기각. 게이트가 이미 피처면 이득이 없다

"0-0 과 2-2 와 3-2 는 투수 행동이 완전히 다른데 모델 하나가 다 배우려 하면 평균만
배운다"는 발상이다. 볼카운트·주자상황·좌우타 같은 상황별로 전문가 모델을 따로 두고
게이트로 고른다.

**로지스틱 검산은 통과했다** (`count_probe.py`, 2024 검증).

```
global (카운트 없음)   338.09     ← 비교 대상 아님
global + 카운트 원핫   349.42     ← 공정한 기준선 (주효과 +11.33)
percell (12칸)         373.45     차이 +24.03   ← 순수 상호작용
```

상호작용은 실재하고 주효과의 2배다. 계수도 체계적으로 갈린다 —
`asof_pitcher_success_rate` 의 표준화 계수가 투스트라이크에서 0.066~0.110,
노스트라이크에서 0.025~0.080 이다. 투수 기량이 결정적인 국면이 따로 있다.

> **원핫을 안 주면 이 검산은 틀린다.** 처음엔 global 에 카운트를 안 주고 재서
> +35.36 을 얻었는데, 그 대부분이 칸별 절편(주효과)이었다. 그건 HGB 가
> `balls_before`/`strikes_before` 로 이미 잡는 것이라 분할의 공이 아니다.
> **분할 모델을 평가할 땐 기준선에 게이트 변수를 반드시 넣을 것.**

**그런데 HGB 로는 크게 진다** (`moe_test.py`, fold 2024 seed 42).

| 구성 | 점수 | 전역 대비 | 낙관 편향 폭 |
|---|---|---|---|
| 전역 baseline | **640.01** (iter 1012) | — | — |
| 게이트 `strikes` (3칸) | 594.66 | **−45.35** | +3.59 |
| 게이트 `count` (12칸) | 496.09 | **−143.92** | +14.33 |

**쪼갤수록 단조롭게 나빠진다.** 시드 노이즈 ±15 를 훨씬 넘어 1시드로도 결론이 선다.

**왜 로지스틱은 이기고 HGB 는 지는가.** 로지스틱은 칸 안에서 상호작용을 표현할
수단이 아예 없어서 분할이 유일한 통로다. HGB 는 트리로 그걸 공짜로 한다. 즉
**+24.03 은 HGB 가 이미 먹고 있던 몫**이었고, 분할은 그걸 새로 얻지 못한 채
학습량만 1/3, 1/12 로 깎았다.

칸별 최적 반복수가 그 증거다 — 전역 1012 인데 칸 모델은 100~477 에서 꺾인다.
학습량이 줄자 훨씬 일찍 과적합에 들어가 깊이를 못 쓴다 (4-5 의 학습량 민감도).

> **일반화.** 게이트로 쓰려는 변수가 **이미 피처면** 트리 앙상블에 하드 MoE 는
> 이득이 없다. 트리는 그 축으로 쪼개는 걸 이미 할 수 있고, 분할은 새 정보를
> 주지 않은 채 표본만 나눈다. MoE 가 힘을 쓰려면 전문가마다 **피처 공간이 다르거나**
> 게이트가 **잠재변수**여야 한다. 주자상황·이닝·좌우타로 게이트를 바꿔도 같은
> 이유로 같은 결과가 날 것이므로 재보지 않았다.

> **측정 함정을 막은 방법.** 칸마다 곡선 최적 반복수를 고르면 자유 파라미터가
> 칸 수만큼 늘어 전역(1개)과의 비교가 불공정해진다. 그래서 **모든 칸이 같은
> 반복수를 쓰고 그 하나만 곡선에서 고르는** shared 를 판단 기준으로 삼았다.
> 실제 편향은 3칸 +3.59, 12칸 **+14.33** 으로 칸 수에 비례해 커졌다 — 막지
> 않았다면 12칸을 −129 로 보고할 뻔했다.

### 4-9. ✅ 상황 조건부 Trackman — **채택 (LB 실측 +10.98).** 단, 시계는 빼야 한다

**결론부터.** 편차 피처 8개는 시즌 경계를 넘었다 — 5회차 814.50 → 7회차
**825.48**. 하지만 같은 아이디어를 **표본 수 컬럼까지 달고** 내보낸 6회차는
**796.24** 로 오히려 잃었다. 이 절의 값어치는 피처 자체보다 **그 둘을 가른
방법**에 있다.

| 회차 | 구성 | 로컬 | LB |
|---|---|---|---|
| 5 | 상황 피처 없음 | 645.54 | 814.50 |
| 6 | 편차 8 + **시계 2** (`tmc_n`/`tmh_n`) | 666.59 | **796.24** ▼ |
| 7 | 편차 8 만 | 667.48 | **825.48** ★ |

> 🚨 **6·7회차의 로컬 점수 차이는 +0.89 인데 LB 차이는 +29.24 다.**
> 로컬로는 두 모델을 **원리적으로 구분할 수 없다.** 구분한 것은
> `era_screen.py` 의 연도 누설 검사였다.

5회차 → 7회차 환산비는 **0.50** (로컬 +21.94 → LB +10.98)으로, 1장이 기록한
보수 환산 0.55 와 맞는다.

Trackman 은 세 번 실패했다(4-4 정적 프로필, 4-4 ID 대체, 4-7 변화량). 네 번째가
통했다. 실패한 셋과 무엇이 다른지가 요점이다.

**메인 데이터의 구종 피처는 투수별 전체 평균 하나뿐이다** — `asof_pitcher_
fastball_rate` 등. trackman 에는 `balls_before` / `strikes_before` /
`batter_hand` 가 있어 **"이 투수가 0-2 에서 변화구를 얼마나 던지는가"** 를 만들 수
있다. 이 값은 **행의 상황에 따라 변하므로** 4-4 가 지적한 "투수당 상수" 문제를
피하고, 4-8 이 보인 "HGB 가 이미 잡는 상호작용"도 아니다 — **train.csv 에 아예
없는 정보라 트리가 만들어낼 수 없다.**

**전제 검산** (`ctx_probe.py`). 물어야 할 것은 "카운트별로 구종이 달라지는가"가
아니다. 그건 리그 경향이고 카운트는 이미 피처다. **카운트 조정이 투수마다
달라야** 새 정보다. 그래서 `s_pc − s_p` 의 투수 간 분산을 표집 잡음과 비교했다.

```
구종 breaking × 볼카운트    신호/잡음  2.92
구종 offspeed × 볼카운트    신호/잡음  3.28
구종 breaking × 타자 좌우   신호/잡음 19.01   ←
```

**편차로 준다.** 조건부 비율을 그대로 주면 전체 비율과 겹치고, 트리는 `A−B` 를
축 수직 분할로만 근사한다(4-5). 그래서 `dev = 조건부 − 그 투수 전체` 를 넣는다.
전체 비율은 이미 모델에 있으므로 dev 가 곧 순수 증분이다.

**결과** (`ctx_feat.py`, 2폴드 × 6시드):

```
both   평균 +29.31   표준오차 4.08   n=12   11/12 플러스
       fold2022  +26.9 +28.7 +51.0 +36.2 +45.2 +23.6   평균 +35.3
       fold2024  +20.5  -2.7 +29.2 +44.5 +23.5 +25.2   평균 +23.4
```

평균이 표준오차의 **7.2배**다. 두 폴드 모두 양수. 5시드 앙상블에서는
**645.54 → 666.59 (+21.05)**.

> **중간에 함정에 빠졌다가 나왔다.** 처음 fold 2024 seed42 에서 `both` 가
> **+20.49** 로 나와 채택 직전까지 갔는데, seed43 이 **−2.74** 였다. 23점이
> 시드 하나로 사라진 것이다. 4-6 이 기록한 그 함정("잎 10→20 이 +23.3" → 실제
> −0.72)에 그대로 걸어 들어갔다. **폴드·시드를 늘려야 결론이 선다.**
> 여기서는 늘렸더니 진짜였다 — 하지만 그건 늘려본 뒤에야 알 수 있었다.

**왜 이건 성공했나.** 4-7 과 비교하면 선명하다.

| | 4-7 변화량 (실패) | 4-9 상황 조건부 (성공) |
|---|---|---|
| 최적 반복수 | 1012 → **617** (과적합 가속) | 1012 → **~855** (신호로 사용) |
| 학습 커버리지 | 30.9% | **63.6%** |
| 값의 성격 | 시즌 산포의 **추정 오차**가 지배 | 구종 비율은 표본 수백~수천으로 안정 |
| 행마다 변하나 | 시즌 단위로만 | **행의 카운트·타자손마다** |

**추론 구현.** 평가 서버에 `trackman_history.csv` 가 있다는 보장이 없어
**조회표를 pkl 에 통째로 담는다**(카운트 6,187셀 + 좌우 1,155셀, 순수 dict).
`script.py` 가 `(pitcher_id, 볼카운트)` 와 `(pitcher_id, 타자손)` 으로 붙인다.
각 행은 자기 조합만 조회하므로 **행 독립**이고, 표의 값은 2019~2024 과거
로그에서 나와 평가 데이터를 일절 참조하지 않는다.

추론 시 결측은 **4.4% / 3.3%** 로 학습 때(22.7%)보다 오히려 낮다 — 추론 표는
전 기간으로 만들기 때문이다.

> **손 인코딩은 추론해서 맞췄다.** 메인 데이터는 `1`/`2`, trackman 은
> `Left`/`Right` 다. 투수 비율이 train 2=74.2% / trackman Right=74.9% 로
> 맞아떨어져 **2=Right, 1=Left** 로 확정했다 (타자도 일관).

#### 무엇이 잘못됐나

**① 표본 수 컬럼은 피처가 아니라 시계였다.**

```
학습 시점 tmc_n 평균   2020 185.8 → 2021 289.0 → 2022 407.2 → 2023 497.9 → 2024 555.9
결측률                 2019 100% → 35% → 26% → 21% → 17% → 23%
```

trackman 이 쌓일수록 셀 표본이 커지므로 `tmc_n` 은 **시즌에 따라 단조 증가**한다.
결측률까지 시즌을 알려준다. 성공률이 해마다 떨어지므로(4-2) 학습 기간 안에서는
이 시계가 **진짜로 점수를 올려준다.** 하지만 2025 에서는 학습 범위를 벗어나
포화되고, 그때는 아무 조정도 못 한다.

분해해보면 시계는 폴드별로 부호가 갈리는 순수 잡음이었다 (`ctx_feat.py --variants
base,dev,n,both`, 2폴드 × 3시드):

```
dev    +28.31   표준오차 4.29   6/6 양수      ← 편차 피처만
n       -0.90   표준오차 5.03   2022 + / 2024 -   ← 시계만
both   +25.60   표준오차 7.07   5/6
```

**`dev` 단독이 `both` 보다 평균은 높고 표준오차는 낮고 부호도 완전히 일치한다.**
제출본은 해로운 컬럼 2개를 이고 나간 셈이다. 기본값에서 제외했다
(`--ctx-keep-n` 으로만 되살릴 수 있게 두었다).

**② 한 번에 두 가지를 바꿨다.** 6회차는 피처 10개 추가 **그리고** `n_iter`
1100 → 900 이었다. 리더보드는 제출 슬롯이 비싼 측정 장비인데 변수를 둘 섞어서,
−18.26 이 어느 쪽에서 왔는지 분리할 수 없다. **LB 비교는 반드시 한 번에 한
변수만.**

**③ 그리고 이게 제일 중요하다 — in-era 검증의 해상도 문제.**

폴드 2022·2024 는 **둘 다 학습 기간 안**이다. 그런데 이 데이터에서 피처 효과의
시즌 간 변동은 이미 기록돼 있다 — ID 복원이 2021 **−9.6** / 2022 **+13.5** /
2024 **+21.6** 였다(4-5). 즉 **효과의 시즌 간 표준편차가 ±20~30 수준**이다.

로컬 +21 짜리 개선은 그 변동폭과 **같은 크기**다. 폴드를 2개 쓰고 시드를 6개
써서 표준오차를 4.29 까지 줄여도, 그건 *측정된 두 시즌 안에서의* 정밀도일 뿐
**다음 시즌으로 넘어갈 때의 불확실성은 전혀 줄이지 못한다.**

> **교훈 — 7회차 결과로 다듬은 최종본.** 처음엔 "로컬 +20 급 개선은 원리적으로
> 보증 불가"라고 적었는데 **그건 과했다.** 7회차에서 같은 크기의 개선이 실제로
> 넘어갔다(로컬 +21.94 → LB +10.98). 정확한 진술은 이것이다.
>
> **in-era 검증은 개선의 *크기*는 재지만 *연도 의존성*은 못 잰다.** 폴드가 전부
> 학습 기간 안이라, 연도를 읽어서 얻은 점수와 진짜 신호로 얻은 점수가 똑같이
> 보인다. 6·7회차의 로컬 차이가 +0.89 인데 LB 차이가 +29.24 인 게 그 증거다.
>
> 그래서 순서를 이렇게 잡는다.
>
> 1. **`era_screen.py` 로 연도 누설부터 거른다** — 피처 하나로 "Y년 vs Y−1년"을
>    가르는 AUC. 단조 증가/감소하면 시계다. 학습 없이 수십 초다
> 2. 통과한 피처만 in-era 로 크기를 잰다
> 3. 그 크기를 **약 0.5 배 해서** LB 를 예상한다 (4·7회차 모두 0.50~0.55)
>
> `tmc_n` 은 1단계에서 걸렸을 것이다(AUC 0.602, 단조). 그 검사를 건너뛴 대가가
> 제출 슬롯 하나와 −18.26 이었다.

| fold | HGB | CatBoost | 델타 |

| 2021 | 1192.79 / 1209.93 | 1256.57 / 1257.85 | +63.78 / +47.92 |

평균 **+64.84**, 표준오차 5.72 — 평균이 표준오차의 **11.3배**다. 4-6 이 정한

**시드 안정성이 특히 다르다.** 같은 폴드 두 시드의 점수 차이가

4-6 이 기록한 "시드 노이즈 ±15" 는 **HGB 의 성질이었지 이 문제의 성질이

**앙상블은 기각했다** (규칙 7·8 대로 재보고 결정). 예측 상관은 0.9688 로
다양성 자체는 있지만, 섞으면 세 폴드 모두 나빠진다.

fold     hgb       cat     50:50    25:75    0:100
2021  1206.46  1270.72   1258.62  1269.68  1270.72  ← 순수 cat 최고

워크포워드 가중치 최적화도 스스로 `hgb=0.10 / cat=0.90` 으로 밀었다.
**다양성이 있어도 한쪽이 확실히 약하면 섞을 이유가 없다.**

> 프로젝트에서 실패한 제출 2건이 전부 환경 문제였다 (6-1, 6-4). 새 의존성은
> 같은 종류의 위험이므로 `verify_submit.py` 4단계를 반드시 통과시킬 것.

#### `season` 은 시계지만 빼면 안 된다

`season` 은 평가 시점에 2025 로 **학습 범위를 완전히 벗어난다.** 시계 컬럼을
빼서 7회차를 벌었으니 이것도 후보였는데, 결과는 정반대였다.

```
2021 +118.4    2022 -30.7    2024 -456.3
```

4-2 가 말한 "성공률이 해마다 떨어진다"를 모델이 읽는 **통로가 `season`**
이었다. 빼면 6년 평균을 예측해 최근 폴드가 무너진다. 2025 에서 값이 범위를
벗어나도 "가장 최근 빈" 취급을 받는 것이 최선의 외삽이다.

> **시계 = 나쁨이 아니다.** `tmc_n` 은 빼서 벌었고 `season` 은 빼면 잃는다.
> 차이는 **그 컬럼이 국면 정보를 나르는가**다. era_screen 의 AUC 는 시계인지
> 알려줄 뿐 빼야 하는지는 알려주지 않는다.

#### 상황별 **성공률** 편차 — 학습 없이 기각

4-9 가 통했으니 같은 구조를 **결과 자체**로 만들면 어떤가 (`dev = P(성공|투수,
카운트) − P(성공|투수)`). 전제 검산에서 죽었다 (`exp/sit_probe.py`).

```
투수 x 볼카운트 12칸   신호/잡음 0.06      투수 x 타자좌우  0.22
투수 x 주자상황 8칸    신호/잡음 0.10      타자 x 볼카운트  0.00
```

4-9 채택 피처가 2.92~19.01 이었다. 여기는 **전부 1 미만 — 관측 분산이
사실상 이항 잡음 그 자체**다. 커버리지는 75~85% 로 충분했으니 4-4 식
"전제부터 틀림"이 아니라 **신호 부재**다.

**왜 구종은 되고 결과는 안 되나.** 성공률은 0.52 근처 동전던지기라 셀당
30~100 구로는 아무것도 못 잰다. 구종 비율은 같은 표본으로도 안정적이다.
**Player ID CTR 이 실패한 것과 같은 뿌리다.**

#### Trackman 물리량 — 다섯 번째 갈래도 닫혔다

4-9 가 쓴 trackman 컬럼은 `pitch_type_group` 과 `rel_speed` 둘뿐이라, 남은
물리량에 같은 패턴을 걸었다. 전제 검산은 통과했다 — spin_rate 6.19/24.39,
horz_break 6.33/6.94, ivb 3.98/4.06 으로 **이미 채택된 `rel_speed`(3.33/1.84)
보다 높다.** 연도 누설도 깨끗했다 (AUC 0.502~0.510).

그런데 학습에서는 fold 2024 가 전부 음수였다 (`tmx_c` −3.9, `tmx_h` −12.4,
`tmx_both` −9.8). **4-7 과 같은 결말이다** — 전제 검사는 가설을 죽일 수는
있어도 살리지는 못한다.

해석: spin/break 편차는 **구종 선택의 결과**라 이미 채택된 구종 비율 편차와
정보가 겹친다. 4-9 가 통한 건 구종이 제구 난이도와 직결되기 때문이고,
물리량 자체가 새 경로를 여는 것은 아니었다.

#### `asof_batter_n` — 2024 에서만 크다

README 7장이 1순위로 적어둔 축이다. 3폴드 x 6시드로 쟀다.

```
2021 -5.4    2022 -7.6    2023 정보없음    2024 +30.5 (6/6 시드 양수)
```

fold 2024 는 시드 6개가 +19.97~+36.29 로 전부 양수다 — 시드 노이즈를 훨씬
넘는다. 그런데 다른 폴드는 작은 음수다.

**처음에 세운 "시계가 학습 범위를 벗어나서"라는 설명은 데이터가 부정했다.**
범위 초과 비율은 오히려 2021 이 19.5% 로 가장 크고 2024 가 6.8% 로 가장
작다. 즉 **기전을 모른 채 단일 폴드 효과만 있는 상태**다. 4-6·규칙 12 에
따라 베이스라인은 바꾸지 않고 **후보 제출본으로만** 만들어 두었다
(`submissions/exp_001_no_batter_n.zip`, 로컬 2024 **699.73**, +32.25).

### 4-11. CatBoost 하이퍼파라미터 — 규제를 올리는 쪽이 맞다

주력 모델이 바뀌었으니 HGB 에서 얻은 결론(잎 10, 최소표본 1000)은 옮겨오지
못한다. 3폴드 x 2시드로 다시 훑었다.

| 축 | 결과 | 판정 |
|---|---|---|
| `border_count` 32 | **+23.25** (SE 4.75) 6/6, 3/3 폴드 | 채택 |
| `l2_leaf_reg` 100 | 32 와 묶어 **+28.27** (SE 2.95) | 채택 |
| `l2_leaf_reg` 300 | +28.14 — 100 과 동일 | 포화 |
| `border_count` 16 | +27.94 — 32 와 동급 | 무차별 |
| `border_count` 8 | +16.07 로 되돌아감 | 과함 |
| `depth` 7 | **−18.25** 유의 음수 | 기각 |
| `depth` 4 / 5 | fold2021 전용 (+93.2 / +39.5), 2022·2024 는 음수 | 기각 |
| `min_data_in_leaf` 1 | 델타 **정확히 0.00** | **무시된다** |

**`border_count` 기본값 254 가 나빴다.** 254 < 192 < 128 < 64 < 32 로 단조
개선되다가 8 에서 꺾인다. 4-1 이 "이 문제는 표현력이 아니라 과신하지 않기
싸움"이라고 한 것과 정확히 같은 방향이다 — 분할 경계를 굵게 잡는 것이 곧 규제다.

**`min_data_in_leaf` 는 무시된다.** 기본 `grow_policy=SymmetricTree` 에서는
CatBoost 가 이 파라미터를 조용히 버린다. 에러도 경고도 없고 점수가 소수점까지
같아서 알았다. HGB 의 `min_samples_leaf=1000` 을 그대로 옮겨 적은 것이었는데
**아무 일도 하지 않고 있었다.**

**두 규제는 대체재다.** border32 (+23.25) 와 l2_30 (+13.80) 을 합치면 가산일
때 +37 이어야 하는데 실제 `b32_l2_30` 은 **+25.00** 이다. 규칙 2 가 상호작용하는
하이퍼파라미터를 따로 묶으라고 한 이유가 이것이다 — 따로 재고 더했으면
+37 을 기대하고 +25 를 받았을 것이다.

**최종 선택은 `b32_l2_100` 이다.** `b32_l2_100_d5` 가 평균 +35.39 로 더
높지만 표준오차 9.30 에 fold2021 (+62.8) 로 쏠려 있다. `b32_l2_100` 은
+36.0 / +22.7 / +26.1 로 균일하고 SE 2.95 다. 규칙 12(폴드 재현성·미래 시즌
일반화 우선)에 따라 균일한 쪽을 택했다.

> **스레드 수가 결과를 바꾼다.** fold2024 seed42 에서 6스레드 717.97 vs
> 11스레드 712.29. 실험 비교 시 반드시 고정해야 한다 — `runner.py` 는
> `hparams.threads` 로 캐시 키에 박는다. 이걸 모르고 샤드 구성을 바꾸면
> 5점짜리 유령 효과가 생긴다.

**반복수는 튜닝하지 않는다.** 규제를 올리자 곡선이 평평해졌다 — fold2024 에서
최적 1020 vs 고정 1200 차이가 +2.72 다(튜닝 전엔 13점). 워크포워드 선택은
−10.60 으로 진다. 학습량 보정 권고가 1400 이라 전체 재학습 1320 이 맞는 구간이다.

**최적 반복수는 학습량과 함께 커진다** (`exp/itercurve.py`, 곡선 캐시에서 계산).

```
fold 2021 (48만행) 최적  300     fold 2022 (73만행) 최적  780
fold 2024 (122만행) 최적 1020    → 2025 (147만행) 권고 약 1400
```

데이터가 많아질수록 곡선이 평평해진다 — 2022 는 600~1200 전 구간이 7점 안에
있다. **2025 는 모든 폴드보다 데이터가 많으므로 반복수 민감도가 가장 낮다.**

### 4-12. 범주형 인코딩 — 카디널리티부터 셌다

규칙 5 가 시킨 순서대로 카디널리티와 범주당 표본 수를 먼저 쟀다
(`exp/card_probe.py`).

| 컬럼 | 카디널 | 범주당 중앙 | 순위상관 | 미지 비율 |
|---|---|---|---|---|
| `pitcher_team_id` / `batter_team_id` | 13 | 137,000 | **−0.12 / +0.15** | 0% |
| `base_state` | 8 | 81,000 | 0.405 | 0% |
| `inning` | 13 | 164,000 | **−0.945** | 0% |
| `game_month` | 8 | 214,000 | **−0.905** | 0% |
| `pitcher_id` | 792 | 856 | −0.280 | 15.7~20.6% |
| `batter_id` | 830 | 473 | −0.253 | 8.8~11.0% |

**`inning` 과 `game_month` 는 순위상관이 −0.9 대라 숫자 취급이 옳다.** 반면
**팀 ID 는 13 범주에 각 137,000 행인데 순위상관이 사실상 0** 이다. 지금
ordinal 정수로 넣고 있으니 트리는 `team_id < 7` 같은 무의미한 축으로 범주를
갈라야 한다. 13 범주면 원핫이 13 컬럼뿐이라 값이 싸다.

> **이건 규칙 5 가 기각한 Team ID CTR 의 반복이 아니다.** CTR 은 타깃 기반이라
> 폴드마다 부호가 뒤집혔다. one-hot 은 **타깃을 전혀 쓰지 않으므로** 그
> 불안정성이 구조적으로 없다. `exp/prep_onehot.py` 를 준비해 뒀다 (미실행).

`pitcher_id`/`batter_id` 는 미지 비율이 9~21% 라 원핫·CTR 둘 다 대상이 아니다.
4-5 의 "ID 를 남기면 +8.5" 는 트리가 구간을 잘게 쪼개 **개체를 식별**하는
것이지 순서를 쓰는 게 아니다.

### 4-13. CatBoost 트리 구조·배깅 — 기본값이 최선

`grow_policy` 는 특히 볼 값어치가 있었다. 기본 `SymmetricTree` 는
`min_data_in_leaf` 를 무시하지만(4-11) `Depthwise`/`Lossguide` 는 실제로 쓴다.

| 변형 | 2021 | 2022 | 2024 | 평균(SE) | 판정 |
|---|---|---|---|---|---|
| `Depthwise` | −150.6 | −45.2 | −35.4 | **−77.06** (23.82) | 유의 음수 |
| `Lossguide` max_leaves 31 | −136.6 | −42.1 | −30.5 | **−69.74** (21.54) | 유의 음수 |
| `Lossguide` max_leaves 10 | +18.3 | −38.1 | −28.1 | −15.97 (11.04) | 부호갈림 |
| `rsm` 0.8 | +4.5 | −4.3 | −3.3 | −1.04 (3.46) | 부호갈림 |
| `subsample` 0.8 (Bernoulli) | +12.3 | −2.7 | +6.3 | +5.28 (5.17) | 부호갈림, 미달 |

**HGB 에서 오래 튜닝해 얻은 모양을 옮기면 손해다.** `Lossguide max_leaves=10`
+ `min_data_in_leaf=1000` 은 4-1 이 찾은 HGB 최적 형태 그대로인데 CatBoost 에서는
**−15.97** 이다. 모델이 바뀌면 구조 하이퍼파라미터는 처음부터 다시 찾아야 한다.

`rsm` 0.8 이 실패한 것은 HGB 에서의 기존 결론과 같다 — 이 데이터에서 피처
서브샘플링은 어느 모델에서도 도움이 안 된다.

### 4-14. 시드 앙상블 — CatBoost 에서도 3개면 거의 끝난다

exp015 로 3폴드 x 6시드(18칸)를 채워 곡선을 완결했다.

```
       2021      2022      2024      평균
k=1  1297.35   2357.70    737.10   1464.05
k=2  1304.09   2363.06    741.22   1469.46
k=3  1306.17   2363.87    742.74   1470.93
k=5  1308.07   2364.97    743.58   1472.21
```

1→3 이 **+6.88**, 3→5 가 **+1.28** 이다. HGB 에서 5→10 이 +0.25 였던 것(4-10)과
같은 포화 형태다.

**제출 경로에서 확인해 보니 3→5 가 −0.63 이었다** (748.77 → 748.14, 4-17). 앙상블
크기를 늘리는 것 자체는 분산 감소라 기대값으로 손해가 아니지만, **실측 이득이 ±1
잡음 안**이라는 뜻이다. 제출본을 다시 만들 이유가 되지 못한다. 이 축은 닫는다.

### 4-15. `lr` 0.01 x `n_iter` 2400 — 실험 경로에서 +5.83, **제출 경로에서 −2.88. 기각**

먼저 실험 경로의 결론부터. `lr` 을 절반으로 낮추고 반복수를 두 배로 올리는 쪽이
맞아 보였다. exp014 를 18칸 전부 채워 판정했다.

```
lr01_i2400   평균  +5.83   표준오차 1.71   n=6   5/6+   부호일치   유의
             2021 +7.9 | 2022 +4.2 | 2024 +5.4
lr04_i600    평균 -14.43   표준오차 4.16   n=6   1/6+   부호일치   유의
             2021 -24.3 | 2022 -15.9 | 2024 -3.1
```

**세 점이 단조다** (0.04 −14.43 < 0.02 기준 < 0.01 +5.83). 그래서 한 칸 더 내려간
`lr` 0.005 x 4800 을 exp016 으로 이어서 쟀다 (4-16).

> 이것은 4-11 에서 "`n_iter` 튜닝은 규제 후 곡선이 평평하다"며 닫은 축과 **다른
> 축이다.** 거기서는 `lr` 을 고정한 채 반복수만 움직였다. 여기서는 `lr` x `n_iter`
> 곱을 유지하며 **한 스텝의 크기**를 줄인다 — 4-1 의 "과신하지 않기" 방향과 같다.

비용은 학습 시간 2배(f2024 셀 105초 → 218초), 추론 시간 2배(3.2초 → 약 6.4초)다.
추론 제한 600초에 비하면 무시할 수 있다.

**그런데 제출본을 실제로 빌드해 보니 부호가 뒤집혔다.**

```
제출 경로 (train_cat.py, 2024 홀드아웃)
  시드 5 고정   lr 0.02 x 1200  748.14   lr 0.01 x 2400  745.26   -2.88
  시드 3 고정   lr 0.02 x 1200  748.77   lr 0.01 x 2400  745.08   -3.69
실험 경로 (exp/runner.py, 같은 f2024)
                lr 0.02 x 1200  738.28   lr 0.01 x 2400  743.66   +5.38
```

**같은 폴드에서 부호가 반대다.** 재실행 잡음이 아니다 — 같은 설정을 다시 돌리면
누적 점수가 748.77 로 소수점까지 재현된다(4-17). 즉 두 경로가 이 크기의 효과에
대해 서로 다른 답을 낸다. 원인과 대응은 **4-17** 에 적었다.

**기각한다.** 학습·추론 비용 2배를 지불할 근거가 제출 경로에 없다.

### 4-16. `lr` 0.005 x `n_iter` 4800 — 기각. lr 축은 여기서 닫는다

4-15 에서 축이 단조였으니 한 칸 더 내려가 봤다 (exp016, 3폴드 x 2시드).
**기준(0.02) 대비로만 보면 유의하다. 그러나 실제로 대체하려는 상대는 0.01 이다.**

```
cat_tuned 대비   lr005_i4800  평균 +8.87  SE 3.19  n=6  5/6+  부호일치  유의
                 lr01_i2400   평균 +5.83  SE 1.71  n=6  5/6+  부호일치  유의

lr01_i2400 대비  lr005_i4800  평균 +3.04  SE 2.50  n=6  4/6+  🚩부호갈림  미달
                 2021 +8.5 | 2022 -0.8 | 2024 +1.4
```

**같은 6칸에서 직접 짝지어 재는 것이 옳은 비교다.** 그렇게 하면 f2022 가 음수로
갈리고 평균이 표준오차의 2배에 못 미친다. 폴드별로 보면 f2021 s43 한 칸(+15.3)이
평균을 거의 혼자 만들었다 — 규칙 ⑤ 가 경고하는 형태다. 비용은 학습·추론 모두
0.01 판의 2배(기준의 4배)다.

> **교훈: 델타는 기준이 아니라 대체 대상에 대해 재라.** 기준(0.02) 대비 +8.87 만
> 보고 채택하면 이미 확정된 0.01(+5.83) 위에 아무 근거 없이 비용 2배를 얹는
> 것이 된다. 축을 따라 개선을 쌓을 때는 **직전 채택본이 새 기준**이다.

실험 경로에서 lr 축의 마진 구조는 이렇게 정리된다 — 0.04 −14.43 (유의 음수) /
0.02 기준 / 0.01 +5.83 (유의) / 0.005 +3.04 (미달). **그리고 0.01 은 제출 경로에서
−2.88 로 무너졌다 (4-15).** 축 전체를 닫는다. 확정값은 **0.02 x 1200** 이다.

### 4-17. 🚩 측정 경로가 두 개였다 — 6점짜리 결론은 경로를 못 건넌다

오늘 가장 비싸게 배운 것. `exp/runner.py`(실험)와 `train_cat.py`(제출)는 **같은
설정에서도 다른 점수를 낸다.**

```
같은 lr 0.02 / f2024 / s42:   runner 733.99   train_cat 747.11   차이 +13.12
```

| | 실험 경로 | 제출 경로 |
|---|---|---|
| 입력 | `exp/cache/X.npy` — **float32** 로 굳힌 행렬 | pandas DataFrame (float64) |
| 범주형 | prep.py 가 미리 정수화 | 파이프라인 안 `OrdinalEncoder` |
| 스레드 | **11** (설정에 고정, 캐시 키에 포함) | 기본값 = 이 PC 에서 24 |
| 폴드 | 2021 / 2022 / 2024 | 2024 하나 |

`border_count` 32 는 **분위 경계를 32개만** 만든다. float32 로 내림한 값과 float64
원값은 경계 근처에서 다르게 떨어지고, 스레드 수는 히스토그램 병합 순서를 바꾼다.
경계가 적을수록 한 표본이 경계를 넘나드는 영향이 커진다 — 규제를 세게 걸어 점수를
얻은 대가로(4-11) **경로 민감도**가 커진 것이다.

**재실행 잡음이 아니라 경로 편향이다.** 같은 경로에서 같은 설정을 다시 돌리면
누적 점수가 748.77 로 소수점까지 재현된다. 두 경로가 각각은 결정적인데 서로
13점 어긋나 있다.

**그래서 무엇을 믿을 수 있는가.** 지금까지 채택한 것들을 두 경로에서 다시 보면
규칙이 뚜렷하다.

| 변경 | 실험 경로 | 제출 경로 | 경로 통과 |
|---|---|---|---|
| HGB → CatBoost | +64.84 | 699.73 → 725.80 (+26) | ✅ |
| border 32 / l2 100 | +28.27 | 725.80 → 748.77 (+23) | ✅ |
| `lr` 0.01 x 2400 | +5.83 | 748.77 → 745.08 (**−3.7**) | ❌ |
| 시드 3 → 5 | +1.28 | 748.77 → 748.14 (**−0.6**) | ❌ |

**경로 편향(±13)보다 큰 효과만 살아남았다.** 20점 넘는 것은 둘 다 통과했고,
6점 이하는 둘 다 부호가 뒤집혔다. 우연이 아니라 규모의 문제다.

> **⑥ 채택은 제출 경로에서 확인할 것.** 실험 경로는 **방향 탐색용**이다 — 빠르고
> 3폴드를 볼 수 있지만 절대 점수가 편향돼 있다. 실험에서 **10점 미만**으로 나온
> 이득은 제출 경로 2024 홀드아웃에서 다시 재기 전까지 채택하지 않는다. 빌드
> 한 번(약 6분, `--save` 없이 검증만)이면 되고, 그게 오늘 두 번 잘못된 채택을
> 막았다.

경로를 통일하는 쪽은 택하지 않았다. 실험 경로의 float32 캐시는 파싱 1~2분과
메모리(가용 7GB)를 아끼려고 만든 것이고, 이걸 버리면 오늘 돌린 60여 칸이
불가능했다. **편향된 빠른 경로 + 제출 경로 확인**이 더 싸다.

### 4-18. CatBoost 범주형(target statistics) — 기각. 주최측이 더 좋은 버전을 이미 줬다

**지금까지 CatBoost 를 '빠른 GBDT' 로만 썼다.** 범주형을 `OrdinalEncoder` 로 정수화해
숫자 피처로 먹였고, 이 라이브러리의 간판 기능인 ordered target statistics 는 한
번도 켜본 적이 없었다 (`exp/runner.py` 가 `cat_idx` 를 계산해 넘기면서도
`cat_features` 로 전달하지 않았다). exp017 에서 처음 켰다.

```
cat_low  (top_bottom/game_type/base_state)      평균  +1.90  SE  3.44  3/6+  🚩부호갈림  미달
cat_ids  (위 + pitcher_id 792/batter_id 830/팀)  평균 -31.17  SE 16.74  1/6+  부호일치   기각
cat_low 대비 ID 효과만                            평균 -33.07            2/6+  2021 -91.0
```

**기전 — `asof_*` 가 이미 같은 정보의 우월한 버전이다.** `asof_pitcher_middle_rate`
는 각 행의 **투구 직전 시점까지**로 계산된 공식 컬럼이다. CTR 은 학습 구간 전체를
하나로 평균하므로 as-of 규율이 없고, 4-2 의 연도별 비율 하락을 그대로 담은 **낡은
수준값**을 실어 온다. 중복인데 편향까지 있으니 해로울 수밖에 없다.

**폴드별 피해 크기가 그 증거다** — 2021 −82.5 / 2022 −10.1 / 2024 −0.9. fold2021 은
2019~2020 만으로 학습하니 투수당 표본이 적어 CTR 이 잡음이고 미지 투수 비율도
높다. 학습 이력이 길어질수록 피해가 줄어든다.

기대했던 부수 효과 — "2025 의 미지 투수가 숫자 외삽 대신 사전값을 받는다" — 는
2024 에서도 나타나지 않았다. 비용은 CTR 계산으로 셀당 **3배**였다.

> **⑤ 가 또 걸렸다.** 중간 결과에서 f2024 s42 가 **+11.65** 로 유망해 보였는데
> s43 이 **−13.42** 로 평균이 −0.9 가 됐다. 한 시드를 근거로 쓰지 않은 것이
> 오늘 세 번째로 도움이 됐다.

### 4-19. 목적함수 RMSE — 기각. Logloss 로 둔다

채점은 Brier(=MSE)인데 `loss_function` 을 코드 어디에서도 설정하지 않아 CatBoost
기본값 **Logloss** 로 학습해 왔다. `CatBoostRegressor(RMSE)` 로 0/1 을 직접 회귀하면
채점 지표를 그대로 최소화한다 — 지표 정렬 논거는 옳지만 점수는 안 따라왔다 (exp018).

```
rmse        (i1200)  평균  +2.64  SE  2.61  4/6+  🚩부호갈림  미달   2021 +5.1 | 2022 -4.4 | 2024 +7.2
rmse_i2400           평균 -54.65  SE 20.28  0/6+  부호일치    유의   2021 -117.7 | 2022 -32.2 | 2024 -14.1
```

**`i2400` 이 알려준 것 — RMSE 는 굶주린 게 아니라 반대로 빨리 과적합한다.** 곡선
최적이 f2021 에서 300~420 반복이다 (Logloss 판은 같은 자리에서 300~360). 반복을
두 배로 늘리면 −54.65 로 무너진다. 1200 은 이미 최적점 이후이므로 "반복이 부족해서
효과가 안 났나"는 가능성은 닫혔다.

부수 소득 — RMSE 는 학습이 더 빠르다 (f2024 셀 88초 vs Logloss 105초). 점수가
같다면 실험 회전용으로는 쓸 만하지만, 채택할 이유는 없다.

> 예측을 `[0,1]` 로 clip 해서 비교했다 (제출 경로 `script.py` 와 동일). 안 자르면
> 회귀 출력이 범위를 벗어나 Brier 가 과대 벌점을 받고, 목적함수 효과가 아니라
> 클리핑 부재를 재게 된다.

### 4-21. 🚩 구조 진단 — 우리가 잃는 점수는 두 종류다 (`struct_probe.py`, 학습 0회)

손잡이를 아홉 개 돌려 통과가 둘이었다. 1등까지 로컬 275점이 남았는데 그 크기는
손잡이로 닿지 않으니, **남은 점수가 어떤 종류인지** 봤다.

#### 수준 이동은 전이된 신호를 전멸시킨다

학습 구간에서 그룹 평균을 구해 2024 에 그대로 쓰면(out) — 예외 없이 **0점**이다.
반면 2024 자신의 평균을 쓰면(in) 크다. **상수 예측은 정의상 0점**이므로 in 은
중심이 맞아서 나온 값이 아니라 순수 해상도다.

```
그룹              범주    out      in
pitcher_id        391    0.0    874.8     ← 우리 모델 전체(734~743)보다 높다
balls_before        4    0.0     26.6
inning             13    0.0     24.2
game_month          8    0.0     17.1
```

**신호는 투수 단위로 크게 있고, '지금 시즌 기준'으로 알아야 한다.** 학습 구간에서
가져온 투수 수준은 쓸모가 없다 — 4-18(CTR −31.17)과 4-22(잔차 타깃 −19.56)가
서로 다른 방식으로 같은 벽에 부딪혔다.

#### Murphy 분해 — 해상도는 시즌이 정한다

```
MSE = reliability - resolution + uncertainty      BSS = (resolution - reliability)/uncertainty

폴드  시드    점수     해상도    어긋남   중심편차   중심교정(오라클)
2021   42  1295.55   1471.2    190.4   -0.0093      +35.01
2022   42  2351.70   2326.4     20.9   +0.0035       +4.99
2024   42   733.99    766.4     43.9   +0.0093      +34.38
```

**해상도가 시즌마다 3배씩 다르다.** 추출 가능한 신호량은 모델 속성이 아니라 시즌
속성이다. LB 864.92 에서 역산하면 2025 의 해상도는 **865 이상**이므로 2024 는
우리가 가진 폴드 중 가장 어려운 해다 — 로컬 748.77 은 비관적으로 편향된 숫자이고,
LB 가 로컬보다 높게 나오는 이유이며 델타 0.485 가 안정적인 이유이기도 하다.

그리고 **어긋남이 실재하는 손실이다.** 2024 에서 43.9, 2021 에서 190.4 다.
이건 신호를 더 찾는 문제가 아니라 **가진 신호가 잘못 눕혀져 있는** 문제다 — 성질이
다르고, 그래서 4-23 이 통했다.

### 4-22. 잔차 타깃 — 기각. `asof` 는 수준을 늦게 따라간다

4-21 의 관측에 대한 직접 대응. `asof_*` 는 그 행 시점까지의 기록이라 2025 행의 값이
이미 2025 를 반영한다(행 독립이라 5) 원칙에 안전). 그래서 타깃을 **그 행 자신의
as-of 수준에 대한 잔차**로 바꿔 학습하고 추론에서 되돌렸다 (exp024).

```
resid_p   (투수)       -19.56   2021 +1.3 | 2022 -39.6 | 2024 -20.3
resid_pb  (투수+타자)   +0.72   2021 +32.0 | 2022 -30.0 | 2024 +0.2   SE 12.01
```

**전제가 반쯤만 맞았다.** `asof` 평균은 시즌 비율과 상관 0.969 로 따라가지만
**기울기가 1.578** 이다 — 통산 누적이라 옛 시즌의 높은 비율을 계속 섞어 늦게
따라간다. 시즌 안에서도 격차가 벌어진다 (2024: 3월 +0.017 → 9월 +0.029). 게다가
모델은 이미 `asof` 를 피처로 같은 정보를 쓰고 있었다.

### 4-23. ✅ `alpha` 보정 — 규제가 가져간 퍼짐을 되돌린다. **두 경로 모두 통과**

`script.py` 는 예전부터 `p' = center + alpha*(p - center)` 를 지원했고 `alpha` 는
1.0 이었다. 4-21 의 '어긋남' 항을 직접 회수하는 손잡이다.

```
워크포워드 (exp/calib.py, 이전 폴드에서만 a 추정)
  fold2022  a=1.1189 (출처 2021)      2365.31 -> 2365.40   +0.09
  fold2024  a=1.0893 (출처 2021+2022)  743.65 -> 761.41  +17.76      평균 +8.92, 2/2 승

alpha 격자 (exp/alpha_pick.py)
 alpha    2021     2022     2024   평균    최악        제출 경로 2024 (c=0.5238)
  1.06  +12.14   +7.77   +14.15  +11.35  +7.77            +11.23
  1.09  +15.13   +5.76   +17.82  +12.90  +5.76            +13.97
  1.12  +16.08   -0.19   +19.23  +11.71  -0.19            +14.79
```

**1.01~1.11 구간은 3폴드 전부 양수다** — 오늘 잰 것 중 유일하게 부호가 일치했고,
유일하게 제출 경로를 건넜다. 당연하다: 이건 학습 경로에 의존하는 효과가 아니라
예측에 대한 **산술 변환**이다.

**기전 — 처음 세운 가설이 틀렸다.** "시드 평균이 퍼짐을 깎으니 되돌린다"고 봤는데,
시드를 1→6 으로 늘려도 예측 표준편차가 거의 안 변하고(2024: 0.0425 → 0.0427)
**단일 시드에서도 최적 alpha 가 이미 1.11** 이다. 원인은 앙상블이 아니라 **규제**다.
`border_count` 32 + `l2` 100 으로 4-11 에서 +28.27 을 얻은 대가로 예측이 중심 쪽으로
눌렸다. **alpha 는 규제가 가져간 퍼짐을 되돌린다** — 두 조치가 서로를 보완한다.

**1.09 를 택했다.** 최적은 1.12 지만 그 값에서 fold2022 가 −0.19 로 내려간다.
제출 경로 최대치의 94%(+13.97/+14.79)를 가져가면서 최악 폴드를 +5.76 로 남기는
거래다 — 평가 시즌의 형태를 모르기 때문이다 (4-2). `clip` 접촉은 0.00% 다.

> **규칙 위반이 아니다.** `alpha` 와 `center` 는 학습 시점에 정해져 pkl 에 담기는
> 상수다. 평가셋 분포를 보고 정하면 4-3 의 위반이 되지만, 여기서는 이전 폴드들에서만
> 추정했다. 추론은 행 독립이다.

> **부수 결과 — 시드 축이 다시 열릴 수 있다.** alpha 를 적용하면 시드 6개가 3개보다
> 세 폴드 모두 좋다 (+3.60/+3.01/+1.23). 다만 제출본은 3시드로 간다 — 864.92 대비
> 변수를 alpha 하나로 유지해야 LB 델타의 출처를 가릴 수 있다 (규칙 ③).

### 4-24. ✅ 10회차 — **LB 912.41.** 환산비 3.40, 예상을 6.8배 넘겼다

`alpha` 1.09 하나만 바꿔 올렸다. 예상은 872 였고 실제는 **912.41** 이다.

```
로컬 762.74 -> LB 912.41      9회차 864.92 대비 +47.49
로컬 델타 +13.97 -> LB 델타 +47.49      환산비 3.40   (지금까지 셋 다 0.485~0.554)
위반판 872.15 를 +40.26 앞선다. 규칙을 지키면서 넘어섰다
```

#### 환산비는 하나가 아니다 — **어떤 Murphy 항을 고쳤는지에 달렸다**

이것이 이번 회차의 진짜 발견이다.

| 고친 것 | 회차 | 로컬 델타 | LB 델타 | 환산비 |
|---|---|---|---|---|
| 해상도 (신호) | 4 | +16.97 | +9.40 | 0.554 |
| 해상도 (신호) | 7 | +21.94 | +10.98 | 0.500 |
| 해상도 (신호) | 9 | +81.29 | +39.44 | 0.485 |
| **어긋남 (보정)** | **10** | **+13.97** | **+47.49** | **3.40** |

**왜 갈리는가.** 로컬 2024 의 어긋남은 43.9 인데(4-21) 평가 시즌의 어긋남은 훨씬
크다. 그 크기는 이미 실측돼 있었다 — **위반 국면 보정이 LB 에서 +57.65 를 벌었다**
(1장). 그게 이 시즌 어긋남의 크기였고, 우리는 그 몫을 합법적으로 회수한 것이다.
로컬에서 재는 이득(2024 기준)은 그 시즌의 어긋남만큼만 보이므로 **평가 시즌에서는
배로 나타난다.**

> **계획에 쓰는 방식이 둘로 갈린다.** 해상도를 올리는 개선은 로컬 델타 × 0.5 로
> 보수적으로 잡는다. 보정(어긋남)을 고치는 개선은 로컬에서 작아 보여도 평가
> 시즌에서 몇 배가 될 수 있다 — 로컬 크기로 기각하지 말 것. 오늘 규칙 ⑥의 10점
> 문턱을 보정 축에 그대로 적용했다면 alpha 를 버렸을 것이다 (로컬 +13.97).

#### LB 두 점으로 평가 시즌을 역산했다

`clip` 이 닿지 않으므로 변환은 선형이고 다음 식이 **근사 없이 정확**하다.

```
MSE(a) = a^2 s^2 - 2a C + var(y) + (c + a(m-c) - r)^2
```

`m`·`s^2`(평가셋 예측의 평균·분산)를 2024 홀드아웃 값으로 대용하고 LB 두 점
(864.92 @ a=1.00, 912.41 @ a=1.09)으로 나머지를 풀면:

```
평가 시즌 비율 r = 0.4784      (2024 는 0.4861 — 하락 추세 -0.0077 지속)
cov(p,y)     = 0.002128     (2024 는 0.001887 — 2025 는 신호가 더 많다)
```

두 값이 독립적인 다른 관측과 맞는다 — 하락 추세(4-2)와, "LB 864.92 에서 역산한
2025 해상도 ≥ 865"(4-21)다.

**민감도** (`m`·`s^2` 를 ±40% 흔들어 재역산):

```

1.20    940.5    946.9    953.5      <- 최악이 가장 좋다. 11회차로 택했다
1.30    937.4    955.8    974.5
1.40    907.1    943.3    980.1      <- 현재보다 낮아질 수 있다
```

> **점 2개로 미지수 2개를 풀었으므로 이 적합은 정의상 정확하고 검증이 불가능하다.**
> 보간이지 검정이 아니다. 11회차(1.20)가 세 번째 점을 주면 그때 비로소 모형을

> 좋고 정보도 얻는다.

> **LB 를 보고 alpha 를 고르는 것은 규칙 위반이 아니다.** 5) 가 금지하는 것은

> 그랬다). LB 점수로 상수를 고르는 것은 모든 대회의 모델 선택 과정이다. 다만
> **다른 위험이 있다 — 평가셋 과적합이다.** 탐침 횟수를 세어 둘 것 (현재 2회:
> a=1.00, a=1.09).

### 4-25. 🚩 지표의 정체 — 점수 = `1e5 * rho^2`. 그래서 로컬 비교 방법이 틀려 있었다

12회차 절편 탐침(934.10)으로 평가셋이 풀리면서 `shift_solve.py` 의 오차식이 실측으로
확인됐다. 거기서 지표의 정체가 나온다.

```
점수 = 1e5 * (1 - MSE/var(y)) = 1e5 * R^2
아핀 p' = A p + B 를 최적으로 고르면  R^2 = rho(p,y)^2
따라서   아핀 최적 점수 = 1e5 * rho^2       (A,B 와 무관)
```

**아핀은 이제 공짜다.** LB 점 4개로 A,B 를 푸는 법을 알아냈으므로 설정을 비교할 때
중심·퍼짐의 어긋남을 점수에 포함시킬 이유가 없다.

| | 원점수 | 아핀 최적 | 차이 |
|---|---|---|---|
| 로컬 2024 (cat_tuned s3) | 748.77 | **780.24** | 31.5 |
| LB 12회차 | 934.10 | **942.46** | 8.4 |

#### 그런데 지금까지 그걸 포함시켜 재고 있었다

`postcal_rank.py` 는 `alpha` 만 격자탐색하고 `center` 는 학습구간 평균에 **고정**한다.
4-21 의 오라클 중심교정이 폴드별 +35.01 / +4.99 / +34.38 이었으니, 설정을 바꿔
중심이 조금만 흔들려도 30점씩 가산·감산됐다는 뜻이다. **"부호갈림" 판정의 상당 부분이
이것 아닌가** 를 의심할 만했다.

#### 쟀다 — 아니었다 (`exp/rho_rank.py`, 재학습 0회)

| 4-22 잔차 타깃 | 전제 성립 | −19.56 |
| 4-26 투수 수준 선형보정 | +33.76, **3/3** | −88.89 / −14.75 / −20.30 |
| 4-27 외부 데이터 상한 | +43.24 / +4.62 / +9.95 | −59.21 / +7.87 |
| 4-28 조건부 아핀 | 10개 그룹 **전부 양수** | 10개 중 WF 평균 양수 **0개** |

> **한 시즌에서 맞춘 관계는 다른 시즌으로 안 넘어간다.** 이 문제의 지배적 성질이다.
> 피처를 더 찾는 문제도, 모델을 키우는 문제도 아니다.

그러면 **왜 `alpha` 는 통했는가.** 그것만 유일하게 **로컬에서 전이시키지 않았기
때문이다** — LB 점 4개로 평가 시즌 위에서 직접 풀었다 (4-24, 4-25). 전이가 실패하는
문제에서, 전이를 안 하는 방법만 살아남았다.

#### 그래서 남은 것의 크기도 계산된다

LB 로 직접 푸는 방식을 조건부로 확장하는 것은 원리상 가능하다. 폴드 내 적합값이
곧 "LB 로 풀었을 때 얻을 값"이다 (둘 다 평가 시즌 자신 위에서 맞추므로). 그런데
**미지수가 그룹당 3개씩(`m_g`,`s_g^2`,`C_g`) 늘고 LB 점 하나가 식 하나다.**

```
전역          미지수 3 (m, s^2, C)      -> 실제로 LB 점 4개 썼다.  얻은 것 +8.4
strikes 3칸   미지수 9                  -> LB 점 9개 이상.        얻을 것 +10.7
count 12칸    미지수 36                 -> LB 점 36개 이상.       얻을 것 +31.7
```

**점당 이득이 전역의 1/5 이하로 떨어진다.** 축을 닫는다.

## 5. 확정된 설정

```powershell
.\venv_submit\Scripts\python.exe final_train.py --leaves 10 --min-leaf 1000 `
    --n-iter 1100 --keep-ids --seeds 5 --save
```

같은 설정을 시드만 바꿔 5개 학습하고 예측을 평균한다. 상황 편차 피처 8개는
기본으로 켜진다 (4-9). **`--ctx-keep-n` 은 쓰지 말 것** — 시계 컬럼이 붙어
6회차에서 LB 를 29점 잃었다.

> **반복수는 1100 이다.** 편차 피처만 쓰면 900(666.60)과 1100(667.48)이 사실상
> 같아서, 5회차와 조건을 맞춰 해석이 깨끗해지는 1100 을 택했다.

```python
HistGradientBoostingClassifier(
    max_iter=1100,            # 전체 재학습 시 +10% → 1210
    learning_rate=0.02,
    max_leaf_nodes=10,
    min_samples_leaf=1000,
    l2_regularization=1.0,
    early_stopping=False,     # 시즌 홀드아웃으로 반복수를 이미 정했다
    random_state=42..46,
)
```

- 전처리: 범주형 3개(`top_bottom`, `game_type`, `base_state`)만 OrdinalEncoder
- **수치형은 passthrough.** `asof_*` 의 결측은 "아직 기록이 없다"는 정보이므로
  중앙값으로 덮지 않는다. HGB 는 결측을 분기 조건으로 직접 학습한다
- 학습 데이터: 2019~2024 전체, 균등 가중
- 피처 **55개** — 기본 47 + 상황 **편차** 8 (4-9). **ID 포함** (4-5).
  표본 수 컬럼(`tmc_n`/`tmh_n`)은 시계라 뺀다
- 축소 보정: 없음 (`alpha=1.0`)
- **국면 보정: 없음.** 규칙 위반이라 제거했다 (4-3)

**추론은 행 독립이다.** `script.py` 는 평가셋의 다른 행에서 얻은 통계를 일절
만들지 않는다. `alpha` 와 `center` 는 학습 시점에 정해져 pkl 에 담긴 상수다.

**시드 앙상블은 쓰고 다양성 앙상블은 쓰지 않는다.** 잎 구성이 다른 모델을 섞으면
예측이 중심 쪽으로 오므라들어, 그 이득의 상당 부분이 중심 보정과 겹친다 (4-5).
시드만 바꾸면 퍼짐은 그대로 두고 분산만 깎는다 — 2024 검증에서 단일 평균 691.4 →
5개 앙상블 697.36 (보정 포함 기준. 보정 없이는 645.54).

### 6-4. pkl 안의 numpy 난수 객체 — 여기서 두 번째로 실패했다

2회차 제출이 평가 서버에서 이 에러로 죽었다.

```
ValueError: <class 'numpy.random._pcg64.PCG64'> is not a known BitGenerator module.
```

`HistGradientBoostingClassifier` 는 학습 중 피처 서브샘플링에 쓰려고
`_feature_subsample_rng` (`np.random.Generator`, PCG64) 를 들고 있고, 이게 그대로
직렬화된다. numpy 는 이 객체의 피클 형식을 버전마다 바꿔 왔기 때문에, **평가 서버의
numpy 가 학습 환경보다 낮으면 로드 자체가 실패한다.** 모델이 좋고 나쁘고 이전 문제다.

근본 원인은 `requirements.txt` 에 numpy 가 없었던 것이다. sklearn 은 `numpy>=1.22`
만 요구하므로, 서버 이미지에 낮은 numpy 가 이미 있으면 **pip 이 그대로 두고 넘어간다.**
sklearn·pandas 만 핀을 박아서는 부족하다.

두 겹으로 막았다.

1. **`requirements.txt` 에 `numpy==2.2.6` 을 핀으로 박는다** — 학습 환경과 일치시킨다
2. **pkl 에 난수 객체를 아예 담지 않는다** — `final_train.py` 의 `strip_rng()` 가
   저장 직전에 `_feature_subsample_rng` 를 지운다. 추론 경로는 `_predictors` 만
   쓰므로 예측은 완전히 동일하다 (5만 행에서 최대 차이 0.00e+00 확인)

**재현과 검증 방법.** 낮은 numpy 환경을 따로 만들어 실제로 재현했고, 고친 pkl 이
통과하는 것까지 확인했다. 앞으로 pkl 형식을 건드리면 이 검사를 다시 할 것.

```powershell
python -m venv oldnp
.\oldnp\Scripts\python.exe -m pip install scikit-learn==1.7.2 joblib==1.5.3 pandas==2.3.3 numpy==2.1.3
.\oldnp\Scripts\python.exe -c "import joblib; joblib.load('./model/rf.pkl')"
```

| pkl | numpy 1.26.4 에서 |
|---|---|
| 수정 전 (제출본) | `ValueError: PCG64 is not a known BitGenerator module` |
| 수정 후 | 로드 성공, 추론 25.0초, 예측 동일 |

> **`requirements.txt` 에는 비ASCII 문자를 넣지 말 것.** 설명 주석을 한글로 달았다가
> 뺐다. 인코딩 해석은 환경에 따라 달라질 수 있고, 이 파일이 깨지면 그대로 실행 실패다.

> **`make_submit.py` 는 `model/` 폴더 전체를 담는다.** pkl 백업을 그 안에 두면
> 제출물에 딸려 들어간다. 백업은 폴더 밖에 둘 것.

### 6-6. 콘솔 인코딩 — 로그로 리다이렉트하면 죽는다

한국어 Windows 에서 파이썬 stdout 은 **cp949** 다. 터미널에 그냥 찍을 때는
넘어가지만 `> log.txt` 로 리다이렉트하면 `—`(U+2014), `→`, `✅` 같은 문자에서
그대로 예외가 난다.

```
UnicodeEncodeError: 'cp949' codec can't encode character '—'
```

`final_train.py` 가 **5개 모델을 다 학습한 뒤 결과를 찍다가** 이걸로 죽었다.
저장 직전이라 40분이 날아갔다. 학습은 멀쩡했고 print 하나가 문제였다.

```powershell
$env:PYTHONIOENCODING = "utf-8"     # 또는 명령 앞에 붙인다
```

**`script.py` 에는 비ASCII 출력을 두지 말 것.** 평가 컨테이너에 `LANG` 이 없으면
파이썬이 stdout 을 ASCII 로 잡는데, 그러면 `submission.csv` 를 다 쓰고도 마지막
print 에서 예외가 나 **0 이 아닌 종료코드**로 끝난다. 채점기가 이를 실패로 볼 수

**2026-08-11 확인 — 후보 구성은 이대로 확정이다.** exp_003 위에 `lr` 0.01 x 2400
(4-15)과 시드 5 (4-14)를 얹어 봤지만 **둘 다 제출 경로에서 부호가 뒤집혔다**
(4-17). 지금 올릴 것은 exp_003 **그대로**다.

> **먼저 올릴 것은 CatBoost 하나다.** ③(한 번에 한 변수)에 따라 두 후보를
> 섞지 않는다. CatBoost 가 통하면 그 위에서 `asof_batter_n` 을 다시 잰다 —
> 모델이 바뀌면 피처 효과도 바뀔 수 있다.

### 다음에 확인할 것 (우선순위 순)

0. **CatBoost 후보 제출** (`submissions/exp_003_catboost_tuned.zip`) — **이제 이것
   하나만 남았다.** 로컬 748.77, 보수 예상 약 866. 오늘 이 위에 얹으려 한 두
   변경이 모두 제출 경로에서 무너져(4-15, 4-17) 후보 구성이 확정됐다
1. ~~**`lr` 0.01 x `n_iter` 2400**~~ — 18칸 다 채웠다 (4-15). 실험 경로 +5.83
   (SE 1.71, 부호일치)인데 **제출 경로에서 −2.88**. 기각. `lr` 0.04 x 600 은
   −14.43, 0.005 x 4800 은 0.01 대비 미달 (4-16). **lr 축 전체를 닫는다**
1-b. ~~**제출본 시드 3 → 5**~~ — 쟀다 (4-14). 3폴드 곡선은 +1.28 인데 제출 경로
   2024 에서 **−0.63**. ±1 잡음 안이라 제출본을 다시 만들 이유가 없다. 닫는다
1-c. ~~**`asof_batter_n` 시계 검토**~~ — 쟀다 (4-10, 4-12). HGB 에서만 나던
   효과였고 CatBoost 에서 사라졌다. 종결
2. ~~**시드 수 늘리기 (5 → 15)**~~ — 쟀다 (4-10). 5→10 이 **+0.25** 로 포화다.
   기대했던 +2~5 는 없었다. 이 축은 닫는다
3. ~~**CatBoost 하이퍼파라미터**~~ — 훑었다 (4-11). `border_count` 32 +
   `l2_leaf_reg` 100 으로 **+28.27** (SE 2.95). 규제 축은 포화라 닫는다
4. ~~**범주형 one-hot**~~ — 쟀다 (4-12). 팀·주자상황 원핫 모두 부호가 갈린다.
   카디널리티 논거는 옳았지만 재현되는 이득이 없었다. 축을 닫는다
5. ~~**CatBoost 위에서 피처 재측정**~~ — `asof_batter_n` 을 쟀다 (4-12).
   HGB 에서 fold2024 +30.5 이던 것이 CatBoost 에서 **+0.9** 로 사라졌다.
   나머지 4-5 항목도 같은 운명일 가능성이 높으니 우선순위를 낮춘다
5-b. ~~**CatBoost 범주형(target statistics)**~~ — 쟀다 (4-18). 저카디널리티 +1.90
   부호갈림, ID CTR **−31.17** (2021 −82.5). `asof_*` 가 as-of 규율까지 갖춘
   우월한 버전이라 중복이고 낡은 수준값을 실어 온다. 축을 닫는다
5-c. ~~**목적함수 RMSE**~~ — 쟀다 (4-19). +2.64 부호갈림 미달. `i2400` 은 −54.65 로
   빨리 과적합한다. 지표 정렬 논거는 옳았지만 점수가 안 따라왔다. 닫는다
5-d. **`asof_*` 축소 (경험 베이즈)** — **남은 유일한 피처 축.** 표본이 적은
   `asof_*` 비율을 리그 평균으로 당긴다. 표본 수 컬럼은 시계라 뺐지만(4-9)
   **비율 안에 표본 수를 녹이면** 시계 컬럼 없이 그 정보를 쓴다. 4-1 의
   "과신하지 않기"와 같은 방향이고, 4-9 에서 통한 것도 수준값이 아니라 **편차**였다
6. **`pitcher_id`/`batter_id` 의 시계 성분** — ID 가 연대순이라 AUC 0.562/0.550
   단조다. 4-5 의 "ID 이득이 최근 폴드일수록 커진다"(2021 −9.6 → 2024 +21.6)를
   설명한다. 다만 4회차에서 LB +9.40 으로 실측됐으니 전부가 시계는 아니다.
   ID 를 **순위가 아닌 형태**로 바꾸면 시계 성분만 뺄 수 있을지 모른다
7. **2023 형 붕괴** — 보험. 평가 시즌이 2023 형이 **아닌 것이 실측으로 확인**됐다
   (보정이 LB 에서 +57.65 로 먹혔다). 이번 대회 점수에는 기여하지 않는다

### 일하는 방식 — 비싸게 배운 것들

> **① 값싼 검산을 먼저 찾을 것.** 가설의 전제가 셀 수 있는 것이면 학습 전에
> 세어본다. `pitcher_id` 대체안은 커버리지만 세어 학습 없이 끝났다 (4-4).
> 단, **전제 검사는 가설을 죽일 수는 있어도 살리지는 못한다** — 4-7 은 전제를
> 통과하고도 실패했다.

> **② 연도 누설을 먼저 거를 것** (`era_screen.py`). in-era 검증은 개선의 크기는
> 재지만 **연도 의존성은 못 잰다.** 6·7회차는 로컬이 +0.89 차이인데 LB 는 +29.24
> 갈렸다 — 로컬로는 구분이 원리적으로 불가능했다 (4-9).

> **③ LB 비교는 한 번에 한 변수만.** 6회차에서 피처와 `n_iter` 을 같이 바꿔
> −18.26 의 출처를 못 가렸다. 제출 슬롯은 비싼 측정 장비다.

> **④ LB 예상은 로컬 개선의 약 0.5 배.** 4회차 0.55, 7회차 0.50 이었다.
> 직선 기울기(1.15)를 그대로 쓰면 과대평가한다.

> **⑤ 단일 폴드·단일 시드를 믿지 말 것** (4-6). 오늘도 fold2024 seed42 에서
> +20.49 를 보고 채택 직전까지 갔는데 seed43 이 −2.74 였다.

> **⑥ 작은 이득은 제출 경로에서 다시 잴 것** (4-17). 실험 경로(float32 캐시,
> 스레드 11)와 제출 경로(pandas, 스레드 기본)는 같은 설정에서도 **13점** 어긋난다.
> 실험에서 **10점 미만**으로 나온 이득은 `train_cat.py` 로 2024 홀드아웃을 다시
> 재기 전까지 채택하지 않는다 — 6분이면 되고, 그게 오늘 두 번의 오채택을 막았다.
> ⑤ 와 짝이다: ⑤ 는 **한 경로 안의** 잡음, ⑥ 은 **경로 사이의** 편향을 말한다.

> **델타는 대체 대상에 대해 재라** (4-16). 기준 대비 +8.87 이어도 이미 채택한
> 것(+5.83) 위에 얹는 것이면 그 둘을 **직접 짝지어** 봐야 한다. 그렇게 하니
> +3.04 / 부호갈림 / 미달이었다. 축을 따라 쌓을 때는 직전 채택본이 새 기준이다.

> **시퀀스 모델(LSTM/Transformer)은 이 대회에서 쓸 수 없다.** 이점이 나오려면
> 평가 시점에 그 투수의 직전 투구들을 입력으로 받아야 하는데, 그것들은 전부
> `test.csv` 의 다른 행이라 5) 원칙이 금지한다 ("행 순서 기반 rolling").
> 2019~2024 이력만 인코딩하는 형태는 합법이지만 `asof_*` 의 재구현에 가깝다.
