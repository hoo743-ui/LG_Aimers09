# LG Aimers 9기 Phase 2 — 투구 제구 성공 확률 예측

투구 직전까지 확인 가능한 정보만으로 각 투구의 **제구 성공 확률**을 예측한다.
평가지표는 **Brier Skill Score** — 확률의 순위가 아니라 확률값 자체의 정확도를 잰다.

```
Score = max(0, 100000 × (1 − Brier / r(1−r)))      r = 해당 평가셋의 실제 성공률
```

즉 **Score ≈ BSS × 100,000**. Brier 를 기준선 대비 1% 줄이면 1000점이다.

## 4. 알아낸 것

### 4-1. 이 문제는 "표현력"이 아니라 "과신하지 않기" 싸움이다

| 모델 | 2024 검증 |
|---|---|
| RandomForest `max_depth=10` (베이스라인) | 415.57 |
| HGB 조기종료 (`validation_fraction=0.1`) | **379.01** |
| HGB 256회 (곡선에서 최적점 선택) | 627.05 |
| HGB L10 `min_leaf=1000` 1000회 | **640.01** |

sklearn 의 조기종료는 **학습 데이터 안에서 무작위로** 10% 를 떼기 때문에 같은
시즌끼리 비교하게 되고, 시즌이 바뀔 때의 일반화 실패를 감지하지 못한다. 그래서
수백 회를 더 돌아 과신 상태로 갔다 (예측 범위가 0.28~0.72 까지 벌어짐).

**반드시 시즌 단위 홀드아웃으로 반복수를 정할 것.** `staged_predict_proba` 를 쓰면
학습 한 번으로 전체 곡선이 나온다 (`diag_curve.py`).

잎 개수 탐색 결과 (2024 폴드):

```
L4  587.99    L7  608.12    L10 640.01 ★    L15 632.38    L31 627.74    L63 602.29
```

L10 근처가 봉우리다. 잎이 적을수록 반복수는 늘어난다 (L31 은 530회, L10 은 1000회).

### 4-2. 타깃 비율이 해마다 떨어지고 있다 — 가장 중요한 구조적 사실

| 시즌 | 실제 성공률 | 누적 `asof_pitcher_success_rate` | `asof_..._prev1_game` |
|---|---|---|---|
| 2019 | 0.5647 | 0.5598 | 0.5613 |
| 2020 | 0.5327 | 0.5472 | 0.5340 |
| 2021 | 0.5328 | 0.5355 | 0.5291 |
| 2022 | 0.5289 | 0.5354 | 0.5268 |
| 2023 | 0.5000 | 0.5237 (**-0.024**) | 0.5044 (-0.004) |
| 2024 | 0.4861 | 0.5114 (**-0.025**) | 0.4884 (-0.002) |

**누적형 `asof` 피처는 경력 전체 평균이라 하락 추세를 뒤늦게 따라간다.** 최근 2년은
0.025 나 뒤처진다. 반면 `prev1_game` 계열은 현재 국면을 거의 정확히 반영한다.

이것 때문에 연도별 난이도가 극단적으로 갈린다:

```
2021 → 1192.84     2022 → 2249.51     2023 → 0.00     2024 → 639.04
```

2023 이 0점인 이유는 명확하다. 2019~2022 에서는 "누적 성공률 ≈ 타깃"(격차 0.005)
이었는데, 그 관계를 배운 모델을 격차가 0.024 로 벌어진 2023 에 적용하니 예측 중심이
+0.0394 어긋났다. 중심이 `d` 만큼 어긋나면 `d²/r(1−r)×100000` 점을 잃는다.

```
0.0394² / 0.25 × 100000 = 621점 손실   →  신호(~600점)를 통째로 상쇄해 0점
```

> **경고**: 2025 에 같은 규모의 국면 이동이 오면 점수가 0에 수렴할 수 있다.
> 현재로선 이를 막을 검증된 수단이 없다 (4-4 참고).

### 4-3. Trackman 은 사실상 쓸 수 없다

```
train.pitcher_id       792명   범위 20,700 ~ 24,633
trackman.pitcher_id    906명   범위 50,008 ~ 71,775,155
교집합: 0명
```

ID 체계가 다르게 익명화돼 선수 단위 조인이 불가능하다 (타자도 동일). 양쪽에 다 있는
`balls_before`, `pitcher_hand` 등으로 상황 집계는 만들 수 있지만, **그건 이미 있는
컬럼의 함수라 트리에 새 정보를 주지 못한다.** 투입 대비 효과가 없어 포기.

### 4-4. 검증했으나 **효과가 없거나 해로웠던** 것들

기각된 가설을 남겨 둔다. 같은 길을 다시 파지 않기 위해서다.

**① 최근 시즌 가중 / 오래된 시즌 배제 → 손해**

| 구성 | 2024 폴드 |
|---|---|
| 전체 균등 | **640.01** ★ |
| 전체 가중 ×1.5 / ×2 / ×3 | 605.93 / 582.59 / 585.46 |
| 최근 3 / 2 / 1 시즌 | 581.42 / 544.61 / 599.14 |

가중을 올려도 중심 편차는 0.0119 → 0.0105 로 거의 안 줄고 데이터 유효량만 깎인다.
**전체 데이터를 균등하게 쓰는 것이 최선.**

**② 중심 편차 보정 → 적용 불가**

연도별 편차가 부호까지 바뀌며 불안정하다.

```
편차: 2021 -0.0097 | 2022 +0.0013 | 2023 +0.0216 | 2024 +0.0119
평균 +0.0063  표준편차 0.0117   ← 표준편차가 평균의 2배
```

전년도 보정을 그대로 이식했을 때:

| 연도 | 원본 | 단순 편차빼기 | 선형보정 |
|---|---|---|---|
| 2022 | 2249.51 | 2201.27 (-48) | 2149.28 (-100) |
| 2024 | 639.04 | 657.20 (+18) | **166.63 (-472)** |

선형보정은 2023 의 기울기(0.1634, 예측을 거의 상수로 뭉갬)를 이식하면서 2024 를
무너뜨렸다. **어떤 보정도 적용하지 않는다.**

**③ 축소(shrinkage) 보정 → 불필요**

최적 선형계수의 기울기가 2021/2022/2024 모두 **1.01 근처**다. 제대로 규제한 L10
모델은 이미 캘리브레이션이 맞아 있다. 과신은 잘못 튜닝된 HGB(379점) 한정 문제였다.

**④ `pitcher_id` / `batter_id` 제거 → 차이 없음**

폴드 2021 / 2022 / 2023 / 2024 평균:

| 변형 | 피처 | 평균 | 차이 |
|---|---|---|---|
| **양쪽 ID 제거** | 45 | **1021.61** | +1.27 |
| 투수ID 제거 | 46 | 1020.44 | +0.09 |
| 전체 유지 | 47 | 1020.35 | — |
| 타자ID 제거 | 46 | 1017.92 | -2.43 |
| ID+팀 제거 | 43 | 999.90 | **-20.45** |

`min_leaf=1000` 규제가 세서 애초에 ID 로 잘게 쪼갤 수 없었다. 상위 3개는 전부
노이즈 범위다. 점수가 같으므로 **2025 신인 ID 노출을 피하는 쪽(양쪽 제거)** 을 택한다.

**단, 팀 ID 는 반드시 남길 것.** 같이 빼면 -20.45 로 확실히 손해다 (특히 2024 폴드에서
639 → 575). 팀 단위 정보에는 실제 신호가 있다.

## 5. 확정된 설정

```python
HistGradientBoostingClassifier(
    max_iter=1000,
    learning_rate=0.02,
    max_leaf_nodes=10,
    min_samples_leaf=1000,
    l2_regularization=1.0,
    early_stopping=False,     # 시즌 홀드아웃으로 반복수를 이미 정했다
    random_state=42,
)
```

- 전처리: 범주형 3개(`top_bottom`, `game_type`, `base_state`)만 OrdinalEncoder
- **수치형은 passthrough.** `asof_*` 의 결측은 "아직 기록이 없다"는 정보이므로
  중앙값으로 덮지 않는다. HGB 는 결측을 분기 조건으로 직접 학습한다
- 학습 데이터: 2019~2024 전체, 균등 가중
- 보정: 없음 (`alpha=1.0`)

## 6. 제출 절차

### 6-1. zip 구조 — 여기서 한 번 실패했다

```
submit.zip
├── model/rf.pkl        ← 폴더 경로는 반드시 슬래시(/)
├── script.py
└── requirements.txt
```

**Windows PowerShell 5.1 의 `Compress-Archive` 는 zip 엔트리 경로를 역슬래시로 쓴다.**
ZIP 규격은 슬래시만 허용하므로, 리눅스 평가 서버는 `model\rf.pkl` 을 폴더가 아니라
그 이름의 파일 하나로 풀어버린다. 결과:

```
FileNotFoundError: './model/rf.pkl' (File: /app/script.py, Line: 119)
```

**반드시 `make_submit.py` 를 쓸 것.** 슬래시로 정규화하고, 묶은 뒤 역슬래시 혼입과
필수 파일 누락을 자체 검증한다.

```powershell
.\.venv\Scripts\python.exe make_submit.py
```

### 6-2. 제출 전 로컬 검증

```powershell
.\.venv\Scripts\python.exe script.py
```

`output/submission.csv` 가 생기고 확률이 0~1 범위인지 확인한다. 모델 파일명은
**`model/rf.pkl` 로 고정**이다 (`script.py` 가 그 이름을 찾는다). 내용이 RF 가
아니어도 상관없다.

### 6-3. 모델 파일 형식

`script.py` 는 두 형식을 모두 읽는다.

```python
# 단일 estimator — 베이스라인 호환
joblib.dump(pipeline, "model/rf.pkl")

# 앙상블 — 예측 평균 후 center 쪽으로 alpha 배 축소
joblib.dump({"models": [...], "alpha": 1.0, "center": 0.5238}, "model/rf.pkl")
```

**커스텀 클래스를 저장하지 말 것.** 평가 서버에서 `joblib.load` 가 클래스를 찾지
못해 실패한다. sklearn 객체와 순수 dict 만 담는다.
